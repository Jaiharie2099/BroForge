# Programmatic campaign authoring

The level is generated by code. The live C# bridge also loads and playtests it programmatically; screenshots are used for visual inspection. See `docs/native-interface.md` for that interface.

`tools/build_high_ground.py` writes the editable one-level campaign from explicit terrain, object and trigger data. `tools/NativeCampaignTool` then loads the installed game's managed assembly and calls its real data APIs to create the local playable campaign package:

```text
Campaign.Deserialize(BinaryReader)
  -> update CampaignHeader metadata
  -> FileIO.SerializeCampaign(campaign, true, true)
  -> native decrypt / checksum / decompression / XML round trip
  -> The High Ground.bfg
```

This is an executable use of the game's internal managed data interface, without starting Unity. It is not a recovered original Unity project or a supported public SDK. The tool is bound to the exact game assembly fingerprint reported in `campaign-build.json`; other builds are untested.

From the workspace root:

The preferred route now accepts a semantic JSON design and creates native game objects directly. See [the tool documentation](../../../tools/NativeCampaignTool/README.md) and `templates/campaigns/high-ground.json`. For example, after building the tool:

```bash
.toolchain/dotnet/dotnet .toolchain/native-campaign-tool/NativeCampaignTool.dll \
  --managed '/path/to/Broforce/Broforce_Data/Managed' \
  --design templates/campaigns/high-ground.json \
  --output 'runtime/native-design-test/The High Ground.bfg'
```

This writes both editable and packaged files. The fixture's editable output matches the verified library file exactly. Constructor defaults can change XML-only fields in the packaged output, so experimental packages stay separate until playtested. The earlier Python-to-native packaging route remains available:

```bash
python tools/build_high_ground.py
python tools/validate_high_ground.py
.toolchain/dotnet/dotnet build tools/NativeCampaignTool -o .toolchain/native-campaign-tool
.toolchain/dotnet/dotnet .toolchain/native-campaign-tool/NativeCampaignTool.dll \
  --managed '/path/to/Broforce/Broforce_Data/Managed' \
  --input 'library/levels/high-ground/The High Ground.bfc' \
  --output 'library/levels/high-ground/The High Ground.bfg' \
  --name 'The High Ground' --author 'Jai'
python -m unittest discover -s tests
```

The native serializer provides the XML header and payload, compression, checksum and encryption required by the game's published campaign loader. The package is local; creating it does not upload anything to Steam Workshop or GitHub. A campaign may contain many levels; this first test intentionally contains one. The header carries its name, author, description, length and game mode. The native XML serializer omits the runtime `isPublished` field; the published loader establishes that state.

The `.bfc` remains editable in the level editor. The `.bfg` is intended for the normal Custom Campaign browser. BroMaker character code and art live in a separate mod installation; they are not embedded in either campaign file.

## Corrected character and cage behavior

- Global hero forcing is disabled (`forcedBro=1000`, the native random sentinel), so a rescue may select a vanilla bro.
- Custom first-spawn selection requires an explicit per-campaign BroMaker policy. A campaign file cannot reference a new character by inserting a made-up HeroType value.
- All four start markers use variation 1, which the game interprets as invisible. Variations are appearance modes, not player indices; other values created unwanted starting cages.
- The rescue cage anchor moved from row 24 to row 25. Native `Cage.PlaceCageBlocks` occupies the anchor row and the row below, across two columns, and attaches to ground two rows below. With the terrace surface at row 23, rows 24–25 must be clear and the anchor belongs at row 25.

Evidence: REA FileIO/Campaign/Cage member record `ev_bc4e1c6717e1025badc736e6140404267d6db9cbb649fc68dbf37df98527adeb`; focused Cage record `ev_7b99052148d6d1ed9127b8ef57e03da09656cdf543757d692e661cbad5074250`. The footprint and spawn visibility findings derive from file-backed CIL; host serialization was executed and its output round-tripped through the installed code. That is separate from in-game rendering or gameplay verification.

The generated campaign leaves hero selection to the native vanilla pool. The generic MCP smoke test validates a separately authored custom preset and its own campaign; it does not imply that every later generated revision has been playtested.
